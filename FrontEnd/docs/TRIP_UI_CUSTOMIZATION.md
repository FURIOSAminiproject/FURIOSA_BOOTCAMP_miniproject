# 여행 계획·결과 화면 커스터마이징

2026-10-26 기준. 운영의 `/trips/new`, `/trips`를 읽기 전용으로 확인하고, 배포 대상 `FrontEnd/v1`의 React 코드·현재 NestJS API와 대조했다. 변경은 저장소 코드에 적용했으며 이 기록 자체가 운영 배포 완료를 의미하지 않는다.

## 화면 분석과 변경

| 항목 | 기존 프로토타입 | 현재 구현에 맞춘 화면 |
|---|---|---|
| 여행 입력 | 서울/제주, 고정 날짜·예산·요청사항, 다수 테마 | 빈 출발·도착 검색 → 결과에서 좌표 선택, 자동차/도보, TourAPI 카테고리·반경 |
| 신청 결과 | AI 팀이 숙소·가격·일정을 모두 확정하는 표현 | 실제 응답의 두 경로·거리·예상시간·경로 주변 장소 |
| 첫 결과 | 제주·경주 예시 일정과 가상 고객·견적 | 조회 전 빈 상태와 여행 계획 시작 버튼 |
| 지도 | 일정 지점을 직선으로 연결하고 GIS 검증을 주장 | ORS 응답의 전체 경로 좌표, 선택 경로의 추천 장소 마커 |
| 장소 | 임의 방문 시각·가격·예약·숙소 설명 | DB가 제공한 이름·주소·카테고리와 경로까지의 근사 거리 |
| 화면 이동 | 신청·시연 상세·보관함·별도 탐색기가 분리 | 01 조건 선택 → 02 경로·장소 비교, 조건 수정으로 복귀 |
| 저장 안내 | 예시 일정이 보관된 것처럼 시작 | 현재 탭의 메모리 유지와 새로고침 시 초기화 명시 |

흰색·따뜻한 배경과 짙은 초록색을 공통으로 쓰고 입력은 번호가 있는 세 구역으로 정리했다. 넓은 화면에서는 선택 내용을 오른쪽 요약에 표시하고, 좁은 화면에서는 세로로 쌓는다. 조회 뒤에는 페이지 상단의 요약·비교 카드부터 읽도록 스크롤을 초기화한다. 장소의 ‘지도에서 보기’는 지도까지 이동하고 팝업을 연다.

## 실제 데이터와 UI의 연결

| 사용자 동작 | 기존 API/처리 | 화면 소비 |
|---|---|---|
| 두 글자 이상 입력 후 600ms 대기 | `GET /api/map/search` → 서버 Pelias | 자동완성 이름·주소 목록, 선택한 좌표만 확정 |
| 출발·도착지/이동 방식 확정 | `POST /api/routes` → ORS·기존 DB 캐시 | 요약 카드에 권장 경로 예상시간·거리 자동 갱신 |
| 분류 읽기 | `GET /api/routes/categories` | DB LEVEL1과 그 자손 LEVEL2·3, 실패/재시도 안내 |
| 경로 찾기 | `POST /api/routes/compare` → 외부 ORS·24시간 DB 캐시·TourAPI DB | `/trips`의 권장/최단 카드, 실제 경로 선, 경로별 장소 |
| 경로 선택 | 반환된 결과 중 선택 | 지도 강조선·장소 목록·마커 교체 |
| 장소 확인 | 반환된 장소 좌표 | 지도 팝업, 새 외부 예약/내비게이션 요청 없음 |

‘최단’은 기존 서버가 ORS에 `shortest`로 요청한 결과이며 지도 화면에서 별도 최단 경로 알고리즘을 실행하지 않는다. 두 경로가 동일할 수 있고 실시간 교통은 반영하지 않는다. 추천은 경로 선 주변 장소이며 자동 경유·방문 순서 최적화·입장 가능 여부를 보장하지 않는다. 지도 타일과 경로의 시점 차이를 안내하며 보정·스냅은 추가하지 않았다.

키·DB 접근은 기존 서버에 유지했다. 새 컨테이너·라이브러리·유료 서비스·스키마 변경은 없다. API 상세는 [route-explorer 안내](../../BackEnd/NestJS/src/route-explorer/README.md)를 따른다.

## 상태와 오류 처리

- `TripWorkspaceProvider`와 순수 reducer가 입력·조회 조건 스냅샷·결과·선택 경로를 소유한다. 두 화면을 오가는 동안 유지하고 새로고침하면 초기화한다.
- 검색어는 좌표 선택과 구분한다. 검색어를 수정하면 이전 선택 좌표를 해제하고, 조건을 바꾸면 이전 결과를 폐기한다. 검색 결과를 선택하기 전에는 경로 조회를 막는다.
- 출발·도착 교환, 새 여행, 로그아웃, 화면 이탈, 조회 취소에는 진행 요청을 취소하고 늦은 응답을 무시한다. 취소만 했을 때는 변경하지 않은 이전 성공 결과를 유지한다.
- 검색 실패·검색 결과 없음·경로 조회 실패·한쪽 경로 실패·장소 추천 실패·추천 없음·후보 제한을 구분한다. 추천 실패를 장소 0곳이라는 정상 결과로 표시하지 않는다.
- 새 지도 팝업은 React 텍스트와 DOM `textContent` 경로를 사용한다. 외부 장소 이름을 HTML 문자열로 삽입하지 않는다.

## 검증과 한계

`FrontEnd/v1`에서 Node 22.23.3으로 다음 검사를 통과했다. 기존 Vite 설정/청크 크기 경고는 남아 있다.

```powershell
npm run lint
npm run build
npm run test:trip
```

`test:trip`은 Node 22.18 이상인 22.x의 네이티브 TypeScript 타입 제거 기능을 사용한다. 새 의존성은 없다. 7개 테스트는 빈 초기 상태, 두 위치 선택 필요, 검색어 수정에 따른 좌표·결과 폐기, 조건 변경 시 결과 폐기, 부분 실패 경로 선택, 새 여행 초기화, API 요청 스냅샷 복사를 확인한다.

실제 브라우저에서는 빈 결과 → 입력 → 검색·선택 → 결과 이동, 조건 수정 후 재조회, 자동차/도보, 권장/최단 전환, 장소 팝업과 지도 스크롤, 검색 실패 후 재시도, 조회 취소 후 늦은 응답 무시, 새 여행 및 새로고침 초기화를 확인했다. 지도 검증에는 실제 외부 Pelias 검색 결과와 ORS 자동차/도보 권장·최단 응답을 기록해 격리된 NestJS API에서 재생했다. 장소 추천 카드는 ‘검증용’이라고 표시한 테스트 데이터이며 운영 TourAPI DB 결과가 아니다. 이 기록 데이터·테스트 API는 제품 코드나 프론트 번들에 포함하지 않는다.

운영 PostgreSQL의 실제 장소 추천, 운영 EC2 배포, 실제 휴대폰 화면은 이 검증에 포함하지 않았다. 기존 프로토타입 문제 F01~F06을 모두 수정했다고 판단하지 않으며 [기존 검토 기록](../REVIEW.md)을 함께 확인한다.

## 2026-10-27: 자동완성과 예상시간 미리보기

검색 버튼을 없애고 기존 검색 API를 입력 대기 후 호출한다. 두 글자 이상·최대 100자이며 한글 조합 중에는 요청하지 않는다. 방향키/Enter 선택, Escape 닫기, 다른 영역으로 이동 시 닫기, 오류 재시도를 지원한다. 새 입력·닫기·화면 이탈은 대기 타이머와 진행 요청을 취소하며 늦은 응답은 표시하지 않는다. 검색 API의 기존 서버 캐시·동시 요청 제한은 유지한다. 별도의 외부 자동완성 엔드포인트나 새 키를 추가하지 않았다.

요약 카드의 예상시간은 선택한 두 좌표와 이동 방식의 권장 경로를 기준으로 한다. 350ms 대기 후 기존 단일 경로 API를 호출하고, 카테고리·반경·여행 이름 변경에는 요청하지 않는다. 위치 선택이 해제되면 숫자를 지우고, 이동 방식을 바꾸면 이전 시간이 아닌 계산 중 상태를 표시한다. 실패는 안내와 수동 재시도를 제공하며, 전체 경로·장소 조회 버튼은 계속 사용할 수 있다. 자동 폴링·실시간 교통 조회·장소 추천의 자동 실행은 추가하지 않았다. 클라이언트 취소가 이미 시작된 서버의 계산 중단까지 보장하지는 않는다.

Node 22.23.3의 타입 검사·상태 테스트 7개·production 빌드를 통과했다. 브라우저에서 자동 추천, 방향키/Enter와 마우스 선택, 자동차/도보 예상시간, 입력 수정 시 이전 시간 제거, 검색 오류/키보드 재시도/정상 복구를 확인했다. 격리 API의 호출 기록은 연속 입력의 마지막 검색어만 받았고, 카테고리·여행 이름 수정은 예상시간 재요청을 만들지 않았다. 이전과 같은 실제 ORS 기록 응답을 재생했으며 운영 API·실제 휴대폰/OS 한글 IME 검증과 구분한다.

## 2026-10-27: DB 분류 계층으로 카테고리 통일

상위 카테고리는 `place_categories.category_level=1` 행의 ID·이름 그대로다. 상세 모달에는 해당 `parent_category_id` 계층의 LEVEL2·3만 표시하고 이름은 모두 `category_name` 원문을 사용한다. TourAPI 콘텐츠 유형 7개는 이 화면의 카테고리 기준에서 제거했으며 DB 조회 실패에도 그 목록으로 대체하지 않는다. 첫 진입은 카테고리 미선택 상태다.

LEVEL1 선택 시 모달이 열리며 상세 복수 선택·검색·적용/취소·Escape·설정 버튼 재편집을 제공한다. 전체 선택은 LEVEL1 UUID 하나, 상세 선택은 LEVEL2·3 UUID들을 기존 `categoryIds`에 합쳐 OR 조건으로 조회한다. 서로 다른 대분류의 전체/상세 선택을 함께 사용할 수 있고, 상위 분류에 이미 포함되는 중복 하위 선택은 정리한다. 대분류 해제 시 그 상세 선택도 지운다. 모달당 최대 20개, 요청 전체 최대 200개이며 서버도 같은 전체 한도를 검사한다.

새 화면은 `contentTypeIds=[]`로 보내고 별도 `categoryFilters`나 유형별 매핑을 만들지 않는다. 기존 재귀 SQL·테이블은 유지한다. 서버의 `contentTypes` 메타데이터는 이전 클라이언트 호환용으로 남지만 새 화면은 읽지 않는다. 새 서버는 `categoryIds` 한도를 10개에서 200개로 확장하므로 큰 선택 요청을 사용하려면 서버도 함께 반영해야 한다.

프론트 11개·백엔드 27개 테스트와 타입 검사·빌드를 통과했다. 운영 공개 분류 API를 GET으로만 읽어 검증 당시 LEVEL1 10개·전체 315개를 확인했다. 이 실제 분류 응답을 격리 API에서 재생해 자연관광 LEVEL2/3와 음식 LEVEL1 전체 조합·취소·요약·결과·전송 ID를 확인했다. 지도는 실제 ORS 기록 응답, 장소는 검증용 데이터를 사용했다. 운영 장소 추천의 종단간 검증과 배포·실제 휴대폰 검증은 포함하지 않았다. 검증 자료는 제품 코드에 넣지 않는다.


## 2026-10-27: 지도 색상 범례

공통 지도 아래에 경로·장소와 OSM 배경 색상을 나누어 설명하는 범례를 추가했다. 실제로 표시되는 선/마커만 안내하며, 결과는 배경 설명을 펼치고 작은 입력 미리보기는 접는다. 색상 공유 상수로 지도·결과 카드·범례의 표현을 맞췄다. [색상 안내·코드·검증](MAP_LEGEND.md)을 참고한다.
