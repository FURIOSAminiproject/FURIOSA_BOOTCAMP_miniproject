# 매일 새벽 1시 TourAPI 수집 배치

NestJS 서버가 실행 중일 때 매일 **01:00:00, Asia/Seoul(한국 시간)**에 TourAPI 변경분을 조회하고 `place_categories`, `places`에 저장한다. 서버·Docker의 기본 시간대가 UTC여도 한국 시간 기준이다. [NestJS 공식 스케줄러](https://docs.nestjs.com/techniques/task-scheduling)를 사용한다.

## 자동 실행과 배포

서버 시작 시 스케줄러가 자동 등록된다. 별도 활성화 설정은 없다. 실제 운영 서버가 읽는 `.env.production` 또는 환경변수에 TourAPI 인증키를 설정하고 새 코드로 서버를 재시작한다. 인증키는 운영 담당자의 키를 사용한다. 아래 수집 범위·예산 설정은 기본값을 그대로 쓰면 생략할 수 있다.

```env
TOUR_API_KEY=운영용_실제_인증키
TOUR_BATCH_LOOKBACK_DAYS=2
TOUR_BATCH_PAGE_SIZE=100
TOUR_BATCH_MAX_PAGES=10000
TOUR_BATCH_STATE_PATH=data/tour-batch/state.json
TOUR_API_MAX_REQUESTS=200
```

개발·운영 모두 서버가 실행되면 다음 한국 시간 01:00에 수집한다. 서버 기동 직후에는 수집을 실행하지 않는다. 필터·배치 설정 오류는 기동 시 알리고, 인증키는 실제 수집 시 검사한다. 인증키가 없으면 해당 배치만 MISSING_KEY로 실패 기록하고 웹 서버는 계속 동작한다.

배포 방식은 기존 구성을 따른다. Compose에서는 새 코드와 잠금 파일을 포함해 이미지를 다시 빌드한다.

```bash
APP_ENV=production docker compose up -d --build backend
docker compose logs -f backend
```

PM2에서는 `npm ci`, `npm run build:prod` 후 기존 ecosystem 설정으로 프로세스를 다시 시작해 변경된 환경을 읽힌다. 단순 파일 수정만으로 실행 중인 서버의 설정이 바뀌지는 않는다. 이번 구현 작업에서 운영 서버 재시작·배포는 실행하지 않았다.

## 수집 범위와 저장

- 기본 범위는 전국의 지원 관광타입 12/14/15/28/32/38/39다. `areaBasedSyncList2`로 표시(`showflag=1`)와 비표시(`0`) 변경분을 모두 조회한다.
- 첫 실행은 한국 날짜의 **2일 전부터** 변경된 자료를 읽는다. 마지막 성공 기록이 있으면 설정한 조회 시작일과 `마지막 성공일 - 1일` 중 더 이른 날짜부터 조회해 중단 기간과 날짜 경계를 겹친다.
- 분류·지역 정보를 준비하고, 장소별 기본 정보와 공통·소개·반복·이미지 상세를 수집한다. 비표시 장소는 비활성화하고 상세는 호출하지 않는다.
- 기존 수집 서비스와 SQL을 공유한다. 내부 UUID·후기 연결을 유지하고 `content_id` 기준 UPSERT로 추가·갱신한다. 내용이 같으면 `updated_at`을 유지하며 수집 시각·출처 메타데이터는 갱신한다.
- 지원하지 않는 관광타입(예: 여행코스 25)은 `ignored`로 집계한다. 지원 타입의 잘못된 장소 정보는 `skipped`다.

이 배치는 **최초 전체 수집을 대신하지 않는다.** 현재 개발 DB의 기존 2개 장소 외에 과거 전체 관광정보도 필요하면 [수집 CLI](../../../docs/TOUR_INGESTION.md)로 최초 수집을 수행한 뒤 매일 변경분을 유지한다. 매일 전국 데이터를 지우고 다시 INSERT하지 않는다.

지역이나 관광타입을 제한하려면 다음 선택 설정을 사용한다. 필터를 비우면 전국 전체 지원 타입이다. 필터 변경 시 다른 범위의 성공 날짜를 재사용하지 않고 기본 조회 기간에서 시작한다. 새 범위의 과거 데이터는 별도 최초 수집 대상이다.

```env
TOUR_BATCH_REGION=26
TOUR_BATCH_DISTRICT=380
TOUR_BATCH_CONTENT_TYPE=12
```

## 성공 기록과 실패 처리

성공 날짜는 `data/tour-batch/state.json`에 저장한다. 별도 DB 테이블은 추가하지 않는다. JSON을 임시 파일에 작성한 뒤 원래 경로로 교체한다. Compose의 `tour-batch-data` 볼륨이 `/app/data/tour-batch`를 보존하므로 컨테이너 교체 후에도 기록이 남는다. PM2는 실행 폴더의 파일을 유지한다. 경로를 변경하면 새 경로의 보존·쓰기 권한도 맞춘다.

다음 조건을 모두 만족해야 성공 날짜를 앞으로 옮긴다.

1. 수집 서비스가 정상 종료했다.
2. 표시·비표시 모두 `nextPages=null`이어서 처리할 다음 페이지가 없다.
3. 잘못된 장소로 건너뛴 `skipped`가 0이다. 미지원 타입 `ignored`는 성공을 막지 않는다.
4. 성공 기록 파일 저장까지 완료됐다.

API 오류·호출 예산 초과·미완료 페이지·잘못된 장소·기록 파일 오류가 있으면 실패를 기록하고 이전 성공 날짜를 유지한다. 이미 성공한 장소 저장은 남고 다음 날 같은 기간을 다시 읽는다. 손상된 성공 기록은 조용히 지우거나 덮어쓰지 않는다. 원인을 확인해 복구해야 한다.

`TOUR_API_MAX_REQUESTS`는 한 실행 전체의 API 요청 상한이며 분류·지역·상세·재시도도 포함한다. 상세는 장소당 최소 네 요청이므로 기본 200회로 모든 변경분을 다 처리하지 못할 수 있다. 이 경우 성공으로 표시하지 않는다. 처리량이 계속 한도를 넘으면 제공기관 한도 안에서 요청 예산을 조정하거나 지역·타입별 실행 범위를 나눠야 한다. 페이지를 버리고 성공 날짜만 옮기는 처리는 하지 않는다.

## 중복 실행과 서버 중단

Cron의 `waitForCompletion`, 실행 중 플래그, 기존 PostgreSQL advisory lock으로 같은 프로세스의 겹친 호출과 같은 DB의 동시 수집을 막는다. 잠금 충돌은 건너뜀으로 기록한다. 매 실행마다 API 클라이언트를 새로 만들어 요청 횟수와 예산을 초기화한다.

운영 배치는 백엔드 한 서버 인스턴스에서 실행하는 구성을 따른다. 현재 Compose/PM2는 백엔드 한 인스턴스 구성이며 성공 기록도 그 배치 인스턴스의 볼륨에 남긴다. DB 잠금은 동시 실행 방지이며 여러 독립 서버에서 날짜별 정확히 한 번 실행을 보장하는 작업 큐는 아니다.

01:00에 서버가 꺼져 있으면 그 시각의 작업은 실행되지 않는다. 다음 실행에서 기존 성공 날짜를 기준으로 조회 기간을 넓힌다. 최초 실행 전의 중단이나 성공 기록 파일 자체가 없는 경우에는 기본 조회 기간만 알 수 있으므로 더 과거 자료는 최초 수집으로 보완한다. 별도 즉시 재시도 타이머나 서버 기동 직후 실행은 추가하지 않았다.

## 로그 확인

`TourBatch` 로그의 JSON `event`로 상태를 구분한다.

| event | 의미 |
|---|---|
| `tour_batch_scheduled` | 기동 시 스케줄 등록 확인. 아직 수집 완료를 뜻하지 않음 |
| `tour_batch_started` | 이번 한국 날짜·조회 시작일·수집 범위 |
| `tour_batch_completed` | 모든 페이지 수집·성공 날짜 저장 완료, 건수·API 요청 횟수 포함 |
| `tour_batch_failed` | 수집/완료 판정/기록 저장 실패, 성공 날짜 유지 |
| `tour_batch_skipped` | 다른 수집 실행 중 |

API 인증키·호출 URL·외부 오류 원문은 로그에 출력하지 않는다. 로그 파일 DB 테이블은 추가하지 않았고 기존 Nest/Docker 로그를 사용한다.

## 검증 기록

검증 코드는 사용자 요청에 따라 저장소 밖 로컬 작업 폴더에 보관한다. 배포 코드·커밋 대상에 포함하지 않는다. 실제 01:00까지 기다리는 대신 Nest 스케줄러에 등록된 Cron 작업의 다음 한국 시간과 콜백 실행을 검사한다.

- Node 22.23.3 배치 전용 검증 17개 통과: 01:00 한국 시간, 설정 없이 실제 Cron 등록·콜백, 키 누락 시 배치 실패와 서버 유지, 조회 기간·중단 기간·필터 변경, 성공 날짜, 불완전 처리·실패·잠금 충돌, 중복 호출, 파일 원자적 교체·손상 거부, 미지원 관광타입 구분.
- 격리 PGlite에서 공유 실행 팩터리→분류/장소 실제 SQL→상세 저장→비활성화→성공 날짜 파일 저장을 연결하고 재실행 시 UUID 유지도 확인했다. advisory lock 응답은 대역이며 실제 동시 DB 세션 검증은 별도다.
- 기존 `npm test`: 로컬 검증 파일 포함 Node 31개 + Jest 4개, 총 35개 통과. `npm run build:prod` 통과. 신규 배치 검증까지 총 52개 통과했다. 배포 커밋에 검증 파일이 없으면 기존 10개만 실행한다.
- 원격 DB 쓰기·실제 TourAPI 호출·운영 배포·실제 새벽 실행은 이 자동 검증에 포함하지 않는다.

## 2026-10-26 책임 분리

수동 입력의 기존 기본값·문자열 변환·범위 제한을 `tour-manual.options.ts`로 옮겼다. `TourBatchRunner`는 필요한 변환 함수만 주입받고, 실행 중복 방지·체크포인트·완료 판정·공통 실패 보고를 담당한다. HTTP 컨트롤러는 `TourBatchCommands`의 run/runManual만 요구한다. 스케줄·수동 경로·응답·기본값과 오류 분류는 유지한다. 수동 실행은 일일 배치의 성공 체크포인트를 변경하지 않는다.

기존 배치 검증 17개와 새 계약 검증을 재실행해 통과했다. 전체 결과와 확장 방법은 [유지보수 안내](../../../docs/ORS_PLACE_MAINTENANCE.md)를 따른다. 수집용 실제 API·원격 DB·새벽 실시간 실행 검증은 수행하지 않았다.
