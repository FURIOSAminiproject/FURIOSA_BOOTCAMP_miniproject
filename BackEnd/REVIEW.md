## 2026-10-28 추가: AI 도착 후 일정 수정 계약

기존 `/api/chat`은 변경 설명만 생성해 화면 일정에는 반영되지 않았다. 새 `/api/chat/revise`는 현재 날짜별 일정과 주변 등록 장소 후보를 AI에 제공하고, AI가 낸 전체 날짜의 장소 ID·시각을 검증한 후에만 수정된 일정을 돌려준다. 존재하지 않는 장소·중복·도착 전·겹치는 방문·유형 불일치·무변경은 적용하지 않는다. DB·모델 실패 시 기존 일정을 유지한다. 여행 결과와 승인 기록은 별도 DB에 저장하지 않으며, 경로·예약 변경 기능은 아니다.

## 2026-10-28 추가: 취향 복수 선택 완료 조건과 숙박 조회 구분

채팅 취향 단계는 선택 한 번으로 완료되지 않으며 여러 답변의 텍스트·카테고리를 누적한 뒤 명시적인 `선택 완료`를 요구한다. 숙박 후보 조회는 `categoryIds`와 별개의 콘텐츠 유형 32 조회라는 점을 테스트로 확인한다. 등록 장소가 없는 경우 빈 후보와 경고를 반환하며 실제 DB 재수집이나 숙소 예약 기능을 추가한 것은 아니다.

가까운 DB 숙박 후보가 없을 때는 관광공사 위치기반 숙박 유형을 실시간 조회하고, 그래도 없으면 DB의 먼 후보를 최대 1000km 범위에서 거리순으로 찾는다. 외부 응답의 유형·좌표·반경을 검사하며 공급원 장애와 전체 데이터 부재 시에는 실제 장소를 꾸며내지 않는다. 춘천시청 좌표로 관광공사 실제 조회 1회에서 숙박 후보 3곳을 확인했으며, 운영 배포와 다른 목적지의 가용성은 별개다.

## 2026-10-28 추가: AI 대화 해석과 도착지 일정 큐레이션

기존 AI 호출은 출발·도착 지명 추출에만 쓰였다. 이제 모델이 2~4단계 자연어의 날짜·시각·이동 의사·취향 테마를 해석하고, 도착지 DB 후보 중 날짜별 방문 장소·순서·시각·체류 시간을 제안한다. 사용자가 최근 대화·여행 조건·후보 장소를 Gemini에 보내는 것을 승인한 뒤 연결했다. 대화에는 최근 6개 메시지의 길이를 제한해 보내고 좌표·장소 객체를 제외한다. 일정 큐레이터에는 취향과 실제 후보의 ID·이름·분류를 보내며 좌표·주소는 제외한다.

모델의 완료 선언, 존재하지 않는 장소 ID, 중복 방문, 도착 전 일정, 도보 이동 부담과 식사 설정 위반은 서버에서 거른다. 모델이 없거나 응답이 유효하지 않으면 로컬 규칙으로 이어진다. 모킹된 모델·DB로 판단 반영과 거부 경로를 검증했으며 실제 Gemini 응답 품질·운영 배포는 별도로 확인해야 한다.

기간 답변이 취향으로 저장되고 기본 driving 및 AI의 step/isReady에 의해 이동 수단 질문 전에 완료되던 경로를 수정했다. 서버는 단계별 답변만 채택하며 이동 수단 직접 확인과 취향 답변까지 완료되어야 준비 상태를 반환한다. API 키 없는 경우도 같은 단계를 따른다. 1박 2일 종료일이 서울 시간대에서 당일로 계산되던 날짜 변환도 순수 날짜 계산으로 대체했다.

검증은 Node 22의 기존·추가 테스트, 프론트 타입 검사·빌드, 별도 로컬 모킹 서버를 통한 실제 브라우저로 수행한다. 원격 DB·유료 Gemini·실제 ORS·운영 배포는 이번 검증에 포함하지 않는다. 브라우저에서 기간 답변 후 이동 수단 대기, 모호한 답변 재질문, 직접 선택 후 취향 질문, 생성 버튼 대기, 1·2일차 서로 다른 DB 후보 대역 표시, 새로고침 복원과 초기화를 확인했다.

## 2026-10-23 추가: Google OAuth 환경 로딩과 콜백 주소

AuthModal의 Google 버튼부터 `/auth/google`, 콜백, 세션 복원까지 추적했다. npm·PM2가 서비스 환경 파일만 읽어 상위 BackEnd 파일의 Google 키를 누락하던 문제를 수정했다. 이제 서비스 파일 → 상위 BackEnd 파일 → 시스템 환경 순서이며 Compose의 두 파일 순서와 일치한다. DB 설정의 무조건적인 `.env.local` 추가 로딩도 제거했다. 로컬 프론트 복귀·CORS 기본값을 실제 Vite 80번 포트의 `http://localhost`로 맞추고 마지막 슬래시를 정리했다.

로컬 환경 파일 6개의 복귀/콜백 URL을 local·development는 `http://localhost`, production은 사용자가 지정한 `https://roadfriendtrip.freeddns.org` 기준으로 갱신했다. 콜백 경로는 `/auth/google/callback`이며 비밀값은 복사하거나 기록하지 않았다. 해당 환경 파일은 Git 추적 대상이 아니므로 운영 서버의 영구 환경 파일에도 같은 URL을 반영해야 한다. Google 콜백의 공인 IP·원격 HTTP·잘못된 경로를 조기에 거부한다. Google Console에는 로컬·운영 콜백을 승인된 리디렉션 URI로 정확히 등록해야 한다.

Node 22.23.3에서 Node 회귀 9개, Jest 단위 8개, 모킹 E2E 1개와 production 빌드를 통과했다. 환경 우선순위, 잘못된 콜백 거부, state 검증, 토큰 교환의 콜백 일치, 세션 복원, CORS origin, production Secure 쿠키를 확인했다. 샌드박스의 루프백 EACCES로 HTTP 테스트는 제한 밖에서 실행했으며 DB·Google 응답은 모킹했다. 실제 Google 로그인·운영 DB·Google Console 변경·서버 배포는 수행하지 않았다. 기존 ITS·ORS 캐시 모킹의 스키마 진단 로그는 인증 검증과 별개다.

## 2026-10-23 추가: ITS·ORS DB 캐시와 만료 정리

실제 배포 대상 NestJS에 routing-cache 모듈과 POST /api/routes, GET /api/traffic을 추가했다. 정규화한 실제 요청 조건과 계약 버전의 해시로 DB 캐시를 읽고, ORS 24시간/ITS 5분 만료 뒤 다음 요청에서 제공자 API를 다시 호출해 컬럼별로 저장한다. 같은 프로세스의 동시 요청은 합치고 ITS 헤더/구간 교체는 트랜잭션으로 처리한다. 새 수집 시각부터 TTL을 계산하며 외부/저장 실패를 성공 결과나 최신 데이터로 대체하지 않는다. 외부 API를 DB 트랜잭션 안에서 호출하지 않는다.

기동 시 캐시 테이블 필수 컬럼을 확인하고 누락을 명확한 로그로 남긴다. 매분 자동 정리 Cron은 테이블별 최대 1,000개 만료 부모 행을 SKIP LOCKED로 삭제하며 ITS 구간은 FK로 연쇄 삭제한다. 조회에서는 만료 시각부터 제외하므로 실제 삭제 주기를 기다리지 않는다. 캐시 히트·갱신 시작·저장 건수·실패 단계·삭제 건수 로그를 추가했다. 기존 TourAPI 새벽 1시 스케줄러는 유지한다. 자동 DDL/마이그레이션, 불필요한 만료 캐시 주기 재수집, ORS·ITS 도로 매칭·정체 보정 시간은 추가하지 않았다.

Node 22.23.3에서 저장소 밖 신규 검증 29개와 기존 npm test 14개(Node 6/Jest 8), production 빌드를 통과했다. 격리 PGlite로 실제 캐시 SQL·재사용/만료/재호출·ITS 교체 실패 롤백·정상 빈 결과·1,001건의 제한 삭제·자식 연쇄 삭제를 확인했고 Mock 제공자+로컬 HTTP로 API·기존 TourAPI/새 정리 Cron 등록을 확인했다. 실제 ORS/ITS API 호출·원격 DB 적용/쓰기·AWS 배포는 이번 작업에서 수행하지 않았다. 검증 코드는 배포 커밋 대상에 넣지 않으며 [모듈 안내](NestJS/src/routing-cache/README.md)에 실행 계약과 검증 한계를 기록했다. 아래 과거 B01~B04·회원 ID 차이 등은 해결된 것으로 표시하지 않는다.

검토일: 2026-10-19. 소스·실행 설정을 확인하고 아래 오프라인 검증을 수행했다. 이 문서는 현재 동작과 미수정 문제를 기록하며, 문제 수정 완료를 의미하지 않는다. P1은 외부 응답 때문에 주요 화면을 사용할 수 없게 되는 경로, P2는 특정 입력·배포 조건의 기능 오류다.

## 확인된 개선 항목

### B01 · P1 · 파싱 가능한 불완전한 AI 응답이 정상 응답으로 반환된다

- 근거: [travel-engine.ts](NestJS/src/travel/travel-engine.ts)의 JSON.parse 뒤 raw.days와 raw.costs 등을 그대로 사용한다. [poetry.service.ts](NestJS/src/travel/poetry.service.ts)는 parsed.poemVerses 등 필수 필드를 검사하지 않는다. responseMimeType만 지정되어 있다.
- 재현: SDK를 스텁으로 대체해 `{"days":[],"costs":{},"selectedAccommodation":{}}`를 반환시키면 빈 일정·비용 객체를 그대로 반환했다. 문학 리뷰에 필수 문학 필드가 없는 JSON을 주면 poemVerses가 undefined였다. 실제 Gemini 요청은 하지 않았다.
- 영향: 예외가 나지 않으면 폴백으로 전환하지 않는다. 프론트가 필수 숫자·배열을 렌더링할 때 오류가 나거나 빈 일정을 정상 결과로 표시할 수 있다. API postJson에도 응답 구조 검사가 없다.
- 개선 방향: 일정·리뷰 응답 스키마와 일수·비용·좌표 등의 조건을 검증한 뒤 채택하고, 실패한 경우 명확한 오류나 검증된 폴백을 반환한다. [프론트 검토](../FrontEnd/REVIEW.md)의 지도 HTML 처리도 함께 확인한다.

### B02 · P2 · 낮은 예산에서 비용 항목 합계와 총액이 다르다

- 근거: 절차적 일정의 숙박/식비/교통/입장료 비율 합계는 약 92%다. reserveTotal은 잔여액과 30,000 중 큰 값인데 totalCost는 요청 예산을 유지한다.
- 재현: 키 없는 제주 일정, 성인 2명, 예산 100,000원에서 항목 합계는 `38,000 + 32,000 + 16,000 + 6,000 + 30,000 = 122,000원`, totalCost는 100,000원, budgetStatus는 OPTIMAL이었다. 예산 100,000원은 서버 입력 검증 범위 안이다.
